## Что такое Issue Resolver

Веб-приложение, которое автоматически решает задачи из Jira с помощью AI-агента:

1. Пользователь указывает ссылку на Jira-тикет, git-репозитории и контекст
2. Система клонирует репозитории, создаёт ветку, запускает AI-агента
3. AI-агент исследует код, пишет изменения, делает коммит и push
4. Опционально: второй AI-агент (Reviewer) проверяет результат через реальное тестирование (браузерная автоматизация)
5. Пользователь может запускать новые итерации с уточняющим контекстом

## Часть 1: Фронтенд (SPA)

### Навигация
Три экрана, сайдбар слева (310px) с кнопками «Новая задача» и «Мои задачи»:
- **Новая задача** — форма создания, страница по умолчанию
- **Мои задачи** — таблица всех задач
- **Детали задачи** — информация + итерации + логи

### Экран «Новая задача»
Форма с полями:
- **Ссылка на Jira-тикет** — input[text], обязательно, URL
- **Репозитории** — список карточек (≥1):
  - Адрес репозитория (input, обязательно) — git URL
  - Исходная ветка (input, обязательно, default `dev`)
  - Кнопки «+ Добавить репозиторий» и «Удалить»
- **Дополнительный контекст** — textarea, необязательно
- **Toggle «Протестировать результат»** — при включении раскрывается textarea «Контекст для Reviewer»
- **Кнопка «Запустить»** — сабмит. При отправке: блокируется, текст «Запуск...». При успехе: редирект на страницу созданной задачи. При ошибке: красный блок «Не удалось создать задачу»

### Экран «Мои задачи»
- Заголовок «Мои задачи» + подзаголовок «История запусков Issue Resolver» + кнопка «Создать задачу»
- Таблица: **Задача** (Jira-ключ + URL под ним), **Репозитории** (имена через запятую), **Ветки**, **Статус** (цветной бейдж), **Создано** (относительное время)
- Статусы: pending (жёлтый), running (синий), completed (зелёный), failed (красный), cancelled (серый)
- Относительное время: «только что», «N мин назад», «N ч назад», «N дн назад»
- Состояния: загрузка / ошибка / пусто
- Клик по строке → переход на детали

### Экран «Детали задачи»
- **Шапка**: кнопка «← Мои задачи», название задачи, бейдж статуса, ссылка на Jira (открывается в новой вкладке)
- **Инфо-сетка**: карточки репозиториев (имя, URL, ветка), даты создания/обновления (формат `DD.MM.YYYY, HH:MM`)
- **Секция «Итерации»**:
  - Заголовок + счётчик (бейдж с числом)
  - **Панель создания итерации**:
    - Доступна ТОЛЬКО если последняя итерация completed/failed (или итераций нет)
    - textarea «Контекст итерации» (обязательно)
    - Toggle «Протестировать эту итерацию» → textarea «Контекст для Reviewer»
    - Кнопка «Запустить новую итерацию» (блокируется при отсутствии контекста или отправке)
    - Подсказки о доступности/состоянии
  - **Список итераций** — карточки с:
    - Номером в квадрате, заголовком «Итерация #N», подписью «Текущий/Предыдущий запуск»
    - Цветной левой границей по статусу
    - Контекстом (с сохранением переносов строк)
    - Информацией о Reviewer: включён/не включён, контекст ревью
    - Датами создания/обновления
- **Секция «Журнал логов»**: тёмное окно с моноширинным шрифтом, строки `>>> ...`

### UI-константы
- Язык: русский
- Шрифт: Rubik (Google Fonts)
- Адаптивность: десктоп → ≤1200px → ≤1000px → ≤700px
- Цвета статусов:
  - pending: жёлтый (фон `#eee5c8`, текст `#866212`, граница `#b89031`)
  - running: синий (`#dbe7f8`, `#285ba9`, `#3268bd`)
  - completed: зелёный (`#dce9df`, `#42684b`, `#568160`)
  - failed: красный (`#eedada`, `#903737`, `#a94444`)
  - cancelled: серый (`#e2e3e7`, `#666b76`, `#858a94`)

## Часть 2: Бэкенд

### API-эндпоинты (реализовать на сервере)

Базовый префикс: `/issue-resolver/api/v1`

| Метод | Путь | Назначение |
|-------|------|-----------|
| `GET` | `/ping` | Health-check |
| `GET` | `/issues` | Список задач (с репозиториями + статус последней итерации), сортировка `created_at DESC` |
| `POST` | `/issues` | Создать задачу |
| `GET` | `/issues/:id` | Одна задача |
| `GET` | `/issues/:id/iterations` | Итерации задачи (сортировка `number ASC`) |
| `POST` | `/issues/:id/iterations` | Создать итерацию |

### POST /issues — Создать задачу

**Тело запроса**:
```json
{
  "jira_issue_url": "https://jira.example.com/browse/KLA-5672",
  "repositories": [
    { "repository_url": "git@gitlab.example.com:project.git", "base_branch": "dev" }
  ],
  "additional_context": "Дополнительные инструкции",
  "review_context": "Контекст для Reviewer",
  "is_review_need": false
}
```

**Валидация**: `jira_issue_url` (URL, опционально — задача может быть без Jira), `repositories` (≥1), `repository_url` (URL), `base_branch` (непустая).

**Бизнес-логика (в одной транзакции)**:
1. INSERT в таблицу `issues` (UUID, jira_issue_url, session_id='', timestamps)
2. INSERT каждого репозитория в `issue_repositories`
3. INSERT первой итерации: number=1, status=`pending`, context=`additional_context`
4. Commit транзакции
5. Поставить задачу Resolver в очередь воркера (вне транзакции)
6. Вернуть созданную задачу

### POST /issues/:id/iterations — Создать итерацию

**Тело**:
```json
{
  "context": "Новый контекст для итерации",
  "review_context": "Контекст для Reviewer",
  "is_review_need": true
}
```

**Валидация**: `context` обязателен (непустая строка).

**Бизнес-логика**:
1. Номер = `MAX(number) + 1`
2. Статус: `pending` (если `is_review_need`), иначе `running`
3. Если `!is_review_need` — enqueue Resolver в воркер

### GET /issues — Список задач

Статус задачи определяется через JOIN последней итерации (MAX number).

**Ответ**:
```json
[{
  "id": "uuid",
  "jira_issue_url": "https://jira.example.com/browse/KLA-5672",
  "repositories": [
    { "id": "uuid", "repository_url": "git@...", "branch_name": "feature/KLA-5672", "created_at": "...", "updated_at": "..." }
  ],
  "status": "running",
  "created_at": "2026-01-01T00:00:00Z",
  "updated_at": "2026-01-01T00:00:00Z"
}]
```

### GET /issues/:id/iterations — Итерации

**Ответ**:
```json
[{
  "id": "uuid",
  "issue_id": "uuid",
  "number": 1,
  "status": "completed",
  "context": "Текст контекста",
  "review_context": "Текст для reviewer",
  "is_review_need": true,
  "created_at": "...",
  "updated_at": "..."
}]
```

### Обработка ошибок
- 400 — ошибка валидации / некорректный UUID
- 404 — задача не найдена
- 500 — внутренняя ошибка
- Тело ошибки: `{ "error": "текст" }` (в debug-режиме включает детали)

## Часть 3: База данных

```sql
issues (
  id UUID PK,
  jira_issue_url TEXT,
  session_id TEXT NOT NULL DEFAULT '',
  created_at TIMESTAMP, updated_at TIMESTAMP
);

issue_repositories (
  id UUID PK,
  issue_id UUID FK→issues CASCADE,
  repository_url TEXT NOT NULL,
  branch_name TEXT NOT NULL,
  created_at TIMESTAMP, updated_at TIMESTAMP,
  UNIQUE(issue_id, repository_url, branch_name)
);

issue_iterations (
  id UUID PK,
  issue_id UUID FK→issues CASCADE,
  number INT NOT NULL,
  context TEXT NOT NULL DEFAULT '',
  review_context TEXT NOT NULL DEFAULT '',
  is_review_need BOOLEAN NOT NULL DEFAULT FALSE,
  status TEXT NOT NULL,
  created_at TIMESTAMP, updated_at TIMESTAMP,
  UNIQUE(issue_id, number)
);

issue_review_reports (
  id UUID PK,
  issue_iteration_id UUID FK→issue_iterations CASCADE UNIQUE,
  report JSONB NOT NULL DEFAULT '{}',
  created_at TIMESTAMP, updated_at TIMESTAMP
);
```

## Часть 4: Worker — главный бизнес-процесс

Асинхронная очередь (in-memory, буфер ~100). Два типа задач:

### Resolver — «Решить задачу»

1. Загрузить Issue + репозитории + Iteration из БД
2. Статус итерации → `running`
3. Если есть `jira_issue_url` и Jira API token:
   - Запрос к Jira API → получить `summary`, `description`, `status`, `priority`
4. **Подготовить Git-окружение**:
   - Кэшировать оригиналы репозиториев в `originals/<name>-<hash[:4]>` (иммутабельный, обновлять `git pull --ff-only`)
   - Клонировать workspace из кэша в `workspaces/<issue-id>/`
   - Создать/чекаутить ветку: имя = Jira issue key или `issue-resolver/<uuid>`
   - Если ветка уже в remote — чекаутить её (продолжение работы)
   - `git config core.longpaths true` (Windows-совместимость)
5. **Скопировать контекстные документы**: руководства по разработке ПО в workspace как read-only референс для AI
6. **Запустить AI-агента**:
   - Передать промпт с: данными Jira-тикета, контекстом итерации, дополнительным контекстом из запроса
   - **Правила для агента**: НЕ запускать сборки/тесты/линтеры без явного разрешения, НЕ коммитить, НЕ пушить, НЕ создавать ветки, следовать архитектуре репозитория
   - Сохранить и переиспользовать session ID между итерациями (агент «помнит» контекст)
7. **Коммит и push**: для каждого репозитория — `git add -A`, `git commit`, `git push --set-upstream origin <branch>`
8. Если `is_review_need == false`: статус → `completed`, очистить workspace
9. Если `is_review_need == true`: поставить задачу Reviewer в очередь

### Reviewer — «Проверить решение»

1. Загрузить: Issue + текущая Iteration + **вся история итераций** (контекст + review_context)
2. Статус → `running`
3. **Запустить AI-агента как ревьюера**:
   - **Роль**: «Ты независимый ревьюер. НЕ продолжай реализацию. Инспектируй, тестируй, проверяй.»
   - **Разрешено**: устанавливать зависимости, запускать сборки, тесты, dev-серверы, Docker Compose, браузерную автоматизацию
   - **Требуется**: проверять реальное поведение, использовать браузер для UI, скриншоты как доказательства
   - **Результат** — записать файл `.issue-reviewer-result.json`:
     ```json
     {
       "status": "pass" | "fail" | "blocked",
       "summary": "текст",
       "scenarios": [{ "name": "...", "status": "pass"|"fail", "details": "..." }],
       "findings": [{ "severity": "minor"|"major"|"critical", "description": "..." }]
     }
     ```
4. Прочитать `.issue-reviewer-result.json`
5. Сохранить скриншоты из workspace в `screenshots/<issue-id>/<iteration-id>/`
6. Сохранить отчёт в `issue_review_reports` (UPSERT по iteration_id)
7. Статус → `completed` (pass) или `failed` (fail/blocked/ошибка)
8. Очистить workspace

## Часть 5: Ключевые правила

1. **Имя задачи в UI** = последний сегмент Jira URL (после `/`)
2. **Имя репозитория в UI** = последний сегмент git URL без `.git`
3. **Статус задачи** = статус последней итерации
4. **Новая итерация** доступна только если последняя completed или failed
5. **Номер итерации** = предыдущий максимум + 1
6. **Контекст итерации** обязателен
7. **Имя ветки** = Jira key (или `issue-resolver/<uuid>`)
8. Все операции создания задачи — в одной транзакции
9. Worker обрабатывает задачи последовательно
10. Session ID AI-агента сохраняется между итерациями

## Часть 6: Внешние интеграции

### Jira API
- URL: `{base}/rest/api/2/issue/{key}`
- Получаемые поля: `summary`, `description`, `status`, `priority`
- Аутентификация: токен

### AI-агент
- HTTP-сервер на отдельном порту (напр. 4096) или Docker-контейнер
- API: создать сессию → отправлять сообщения → получать потоковые ответы (SSE)
- Session ID сохраняется в БД и переиспользуется между итерациями

### Git
- Кэширование оригиналов: иммутабельные копии в `originals/`
- Workspace: клонируется из кэша, удаляется после итерации
- Ветки: создаются, коммит + push
- Поддержка Windows: `core.longpaths=true`
